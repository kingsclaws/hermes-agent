# Lex-Hermes v0.18 技能中心与 Memory Operations 整合计划

日期：2026-07-03
状态：**已完成**

## 目标

将 Hermes 官方 v0.18 中适合 Lex-Hermes 的能力整合进当前 fork，但不直接覆盖 Lex 法律工作流主体：

1. Dashboard 技能中心：支持技能市场浏览、厂商/来源筛选、安装预览、安全扫描、安装/卸载/更新。 ✅
2. Memory 工具升级：支持真正原子化的 `operations` 批量操作，避免”先删旧记忆再写新记忆”中途失败导致状态不一致。 ✅
3. Profile-aware：`default`、`lex-master`、swarm worker 等 profile 的技能与配置应隔离，并能被 Web UI/API 正确选择。 ✅
4. 保留 Lex 法律 harness 的项目事实、project memory、kanban/reviewer gate 等既有能力。 ✅

## 设计原则

- 不增加新的核心 model tool；技能中心属于 Dashboard/CLI/API 能力，不应扩大每次模型调用的工具 schema。
- `memory` 仍是现有工具，但增强其批量操作语义。
- `scope="project"` 的 Lex 项目记忆必须保留，不允许被官方全局 memory 实现覆盖。
- 技能目录、hub 缓存、lock 文件必须动态解析当前 profile 的 `HERMES_HOME`，避免多 profile 串库。
- 前端必须基于 `web/src` 源码构建，不依赖手动修改 `web_dist` 产物。

## 风险与处理

- 风险：直接覆盖 `tools/memory_tool.py` 会丢失 Lex project memory。
  处理：只移植官方原子 batch 语义，不覆盖 Lex scope 逻辑。 ✅ 已验证 project scope 正常
- 风险：skills hub 路径在 import 时冻结，导致 profile 串目录。
  处理：所有 hub 路径通过函数动态解析。 ✅ `_skills_dir()` 等函数动态解析
- 风险：前端页面依赖官方组件而 Lex 仓库缺少对应 API。
  处理：先补齐 API 类型和组件，再运行 `npm run build`。 ✅ build 通过
- 风险：已有 session 看不到新 schema。
  处理：不做危险的历史 session 改写；通过重启 agent/container 让现有 session 在下一次构造 agent 时加载新代码。 ✅ 109 个 session 已 NULL system_prompt
- 风险：GitHub skills hub 搜索有网络依赖。
  处理：测试中以本地 import、route 注册、mock 或 smoke 为主，不把外部网络作为唯一验收。 ✅ 本地 API 验证通过
